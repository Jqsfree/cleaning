## 1. 任务目标（最终定义）

一条视频/片段判定为**有效样本**，需同时满足：

```
valid = human_present == 1        # 画面中出现真实人类(非CG/游戏/动画)
        AND crop_interaction == 1  # 该真人对农作物/植物有可见的动作接触
```

不要求具体是「采摘」还是「种植」或其他细分动作，**只要是真人对作物的可见交互，都算有效**（采摘、种植、除草、浇水、修剪、分拣、清洗均可）。具体动作类型只作为可选的描述性字段记录，不作为主过滤条件。

**明确排除**（agent 遇到以下情况直接判负，不需要请示）：

- 无人出镜（纯航拍/固定机位拍摄农田、机械无人自动作业）
- 有人出镜但不接触作物（讲解、走动、面对镜头介绍、纯采访、驾驶机械但手未接触作物）
- 非真人画面（游戏、CG、动画，如农场模拟类游戏画面）
- 人接触的对象已脱离种植环境（市场称重、厨房切菜——这类若清洗中发现占比较高，需上报，不要自行决定是否放宽边界）

## 2. 标注 / 打分 Schema（统一版，所有阶段复用）

```
video_id, keyword, channel, duration_seconds,
human_present:      {0, 1}
human_synthetic:    {0, 1}   # 是否CG/游戏/动画(需配合human_present使用)
crop_interaction:   {0, 1}   # 主过滤字段
mechanized_only:    {0, 1}   # 是否仅机械操作、无人手交互
action_free_text:   可选文本  # 记录具体动作类型,仅用于事后统计分布,不参与过滤
scene_type:         {agri_field, market_kitchen, indoor_garden, game_cg, machinery_ad, mixed_vlog, other}
qc_confidence:       可选,标注者把握程度
```

所有阶段的中间产出、人工复核表，都用这套字段，不要各阶段各自发明新字段。

## 4. 清洗流水线（本阶段执行范围）

| 阶段 | 内容 | 方法 | 输入→输出粒度 |
|---|---|---|---|
| Stage -1 | 元数据文本过滤 | 加载已有模型，阈值 0.3 | 候选列表→通过/reject 标记 |
| Stage 0 | keyword 黑名单过滤 | 对照 `blocklist_keywords.csv` | 同上 |
| Stage 1 | 场景相关性粗筛 | CLIP，宽松阈值保召回 | 视频→pass/reject |
| Stage 2 | 场景多分类 | 多帧输入+冻结特征+分类头，输出 `scene_type`，显式区分 `no_human`/`human_no_interaction` 两个负类 | 视频→scene_type |
| Stage 3 | 人-作物交互检测（**主力方案**） | 人体检测 + 手部接触检测(如 100DOH) + 开放词表作物检测(如 Grounding DINO)，手部检测框与作物检测框重叠/邻近且处于接触状态 → `crop_interaction=1` | 视频/片段→human_present, crop_interaction |
| Stage 4 | VLM 结构化复核 | 仅对 Stage2/3 中置信度样本，二元问题：「是否有真人用手/身体直接接触农作物」，不问具体动作类型 | 边界样本→最终标记 |
| Stage 5 | 人工抽检 | **分层随机抽样**（不是只抽高置信度部分），按新 schema 打标 | 抽样结果→整体合格率估计 |

**Stage 3 补充**：可用轻量监督分类器（冻结特征+分类头，标签为 `crop_interaction` 二分类）作为交叉验证，与检测器组合方案对比一致率，不一致的样本优先送人工复核。

## 5. 执行边界：agent 可自主执行 vs 必须停下等待确认

**agent 可以自主执行、无需请示：**

- 按上述 Stage -1~4 跑既定流水线逻辑
- 按第 1 节的排除规则直接判负
- 按第 3 节直接复用已有脚本/模型/黑名单
- 记录每阶段的通过率、reject 原因分布，写入日志

**agent 必须停下、汇报后等待人工确认，不能自行决定：**

1. **Stage 3 检测器阈值的校准**（IoU 重叠阈值、接触判定阈值）——需要人工标注一批数据做校准，不能拍脑袋定
2. **任何一个 Stage 的通过率/拒绝率相比历史出现异常波动**（比如某阶段拒绝率突然从 30% 变成 70%）——先报告，不要继续往下游跑
3. **Stage2 场景分类里 `market_kitchen` 边界的处理**（人接触的是脱离种植环境的食材，算不算有效）——这个边界在第 1 节里标了「需上报」，agent 遇到高占比时要停下汇报，不能自行放宽/收紧标准
4. **对已有 10.8 万 h 产出的重新验证**（见第 6 节）——这批数据是用旧标准筛出来的，重新按新 schema 抽检后，如果合格率明显偏离预期，要报告，不能自动决定是否作废重跑
5. **是否需要针对某类样本重新训练 Stage2/3 模型**——只在明确指令下重训，不要自主触发

## 6. 已知风险，agent 执行时需要主动核查并汇报

1. **CLIP v1.1 这一刀（125 万→47 万行）从未做过独立误杀率验证**。建议：从被这一轮拒绝的样本里随机抽样（不是抽通过的），按新 schema 人工复核，统计误杀率。这是当前流程里最大的未知风险，优先做。
2. **历史 1461 条 T/F 标注的标签口径需要核实**：当时标注标准是否已经隐含「真人+可见交互」，还是更宽松的「画面里有农田/作物就算」。建议先抽 30-50 条历史 T 样本，按新 schema 重新判一遍，看一致率。一致率低的话，Stage -1 的元数据模型和 Stage3 的交叉验证分类器都需要用新标注重新训练/校准。
3. **缩略图探针（thumb_lr v1/v2）用单帧判断，代表性存疑**，不应继续作为最终判据，本流程已用 Stage2 多帧场景分类替代其角色，旧的 thumb_lr 产出（10.8 万 h）需要重新过一遍新流水线验证，不能直接当作最终结果使用。
4. **query 模板混淆**：早期分析发现 `hand`、`planting` 等词在旧模型系数里显示负向，是 keyword 模板历史通过率的混淆，不是真实语义负向，**不要**把这类词系数当规则写进任何黑名单，只有 `blocklist_keywords.csv` 里明确列出的 keyword 可以拉黑。

---

## 7. 采集环：本阶段不启动，触发后再执行

**当前阶段范围不包含采集环**，agent 只处理已有候选池的清洗。以下触发条件满足时，agent 需要**上报**（不自行采集），由人工决定是否启动新一轮采集：

| 触发条件 | 说明 |
|---|---|
| 清洗后合格样本总时长，距目标缺口 > 30% | 说明现有候选池不够用 |
| 某个 `scene_type` 负类目占比连续两轮 > 15% | 说明源头污染严重，需要从采集侧堵，仅靠清洗兜不住 |
| Stage5 人工分层抽检真实合格率，与流水线预期合格率偏差 > 10 个百分点 | 说明某一级过滤器失准 |

触发后需要做的事（人工决策，agent 仅提供数据支撑）：

- 输出当前各 keyword/channel 的历史通过率统计，供人工设计新采集模板
- 高产句式模板（历史通过率≥60% 的 keyword 对应句式）可作为新模板参考起点
