# metadata 基础设施 v3

2026-09-21。本轮实现统一命令、批次状态与索引、执行恢复、配置修复，以及可选的分层误删验收。入口是 `02_脚本/pipeline/metadata.py`，原 topic_loop 命令作为兼容包装保留。

## 批次执行与状态

`start` 按 policy.category 创建唯一批次，登记绝对输入路径和完整 SHA256。每次执行使用新的 attempt 目录，保存原配置及其哈希；执行失败仍保留 operation 和错误信息。模型、参考人标和输入在执行前后检查内容身份。

`retry` 只恢复失败/中断操作，沿用同一输入、策略、模型、目标、抽样量和随机种子，重新计算到新尝试目录。已有完整候选的尝试不能通过 retry 反复抽样。输入快照在同品类内已有登记时，start 不能换批次名再创建一个 candidate。显式 regression 可以重复实验，但不能交付。

`specialist` 必须有上一轮真实 failed_acceptance，使用同一批次输入，保持合格率目标、损失上限和抽样配置；父轮已见人标继续记为开发数据。执行错误和证据不足不等于人工验收失败，不会自动触发专项。

`status` 默认重新校验输入、三池、候选身份、人标快照和实际验收计算。不能仅编辑 evaluation 的 status 字符串来获得 accepted。`--quick` 明确标为未核验，永不报告可发布。`next` 也改用相同的证据检查。

`publish` 核验最新候选、批次身份、人标、目标与文件内容后原子导出并登记。重复调用只接受内容和原证据均一致的既有 release；不会覆盖已有数据。旧 orchestrate 的 exo 交付也必须登记输入，旧 SOP 的“交付完成”检查追溯原候选与人验。

`catalog` 扫描批次 manifest 重建 JSON 索引，列出品类、批次、已登记阶段/路径、文件是否存在及大小、尝试、状态和下一步。默认不哈希生产大表；相对路径的旧引用明确标为未解析。`--out FILE` 保存可重建快照，不新增需要手工维护的权威数据库。内容校验可通过 `--verify` 开启。

现有 9 个历史批次按 legacy_unverified 展示；这表示缺少本版管理/核验链，不等于历史上没有交付，也不改写历史事实。旧的散落 topic 轮次会作为未托管参考列出；历史普通阶段只列出 manifest 已登记的路径，未登记的大表还需后续整理。

## 抽样与误删验收

运行前可传 `--audit-sizes KEEP DROP REVIEW` 固定各池样本量；未传则各池使用 `--sample-size`。每池采用独立种子的均匀 reservoir 抽样，全池小于样本量时做全量审阅。计划保存在 acceptance_plan 中并绑定候选指纹，所有请求的样本标完才判断。

`--max-t-loss` 是可选业务约束，不设隐含默认 SLA。未配置时保留原来的 keep 合格率判定，不宣称已经控制全链路误删。配置后估计以下保守损失比例：

`drop 中的 T+U / (drop 中的 T+U + keep 中的 T + review 中的 T)`

各池计数先用 `池总量 × 样本比例` 估计，不能直接相加三个样本中的 T。drop 的 U 按潜在误删计算；其他池的 U 不扩大分母。它是保守风险指标，不是把 U 的人标改成 T，也不等同于已知 T 的精确召回率。

对三个池比例使用 Bonferroni 调整的 Wilson 区间，六个尾部各分配 0.1/6，总体目标为约 90% 同时覆盖；Wilson 是近似方法，不宣称精确有限样本保证。全池审阅使用实际比例。损失区间通过分层计数上下界组合得到；同时使用调整后的 keep T 下界判断合格率。

- keep 下界达标，且损失上界不超过限制：accepted。
- keep 上界仍低于目标，或损失下界已经超过限制：failed_acceptance。
- 两者之间：inconclusive，禁止发布，审查预先约定的抽样协议。

如果无法观察到足够 T，损失上界可以很宽；零观察误删不等于总体没有误删。本版没有“多抽几次直到过关”的自动补样。后续若需要顺序抽样，应另行实现预先约定的检验方案。上述总体估计只适用于当前批次的随机审计；历史 gold 回放仍为 retrospective。

## 旧路径修复

- manifest JSON 损坏时明确报错，不再静默覆盖为空；init/update 的读改写使用锁，JSON 用独立临时文件原子替换。新批次绑定输入内容，文件同名但内容变化会阻止复用阶段状态。
- 规则命中缓存离开源码目录，默认在系统临时目录的用户专用 exo-cache 下；可通过 `EXO_CACHE_DIR` 指定。缓存键包含规则目录和 blacklist 内容哈希，规则变化不会沿用旧统计。缓存不可写时不阻止清洗。
- cook blacklist 中 33 条频道 regex 的 TOML 字符串转义已修复，保持原正则意图；这不是对黑名单语义的认可或重新验收。50 个品类 TOML 均能解析。
- 医疗特征测试对齐源码和现有 calibration 已声明的 title+channel，继续明确排除 keyword 和 description；模型实现和权重未变。
- 忽略 `.venv`、测试缓存和指定运行锁，避免它们混入源码变更。

## cook 打分 checkpoint

`score_exo_cook_text.py` 使用共用的 `core/scoring_checkpoint.py`。checkpoint 绑定输入、模型、阈值、校准文件、特征/打分/恢复代码、设备和编码 batch 配置。每个 chunk 写入并 fsync 后，原子提交字节位置、行数和输出哈希。

续跑前验证已提交字节；只允许回退本工具未提交的尾部。已完成文件被修改、同名输入内容变化、模型或阈值改变，均拒绝续跑。没有可信 checkpoint 的旧输出不能只凭行数续跑。非 resume 不再隐式覆盖输出，应使用新路径。

续跑后统一从完整 scored 文件重建 keep/drop，保证行数、时长统计包含之前的 chunk，并避免 CSV 中间重复 BOM。分流阶段若中断，checkpoint 不标记 complete，下次可重建；外部消费者应确认 checkpoint.state=complete。两个独立 CSV 的替换不是单个文件系统事务，不能忽略 checkpoint 直接消费半完成分流。

缺少所选校准阈值时明确报错；可显式传 --threshold。选 strict/recall 也不再静默回退其他模式。该旧打分器产物不具备新 pipeline 的交付资格，仍须独立验收。其他品类旧打分器尚未全部迁移到此恢复模块。

## 验证与实际边界

本轮用历史 cook 的 255 条人标通过 start → 人标回放 → status → publish 阻断验证新入口：keep 仍为 48 T / 73 F，回放质量判决 failed_acceptance，模式为 retrospective_replay_not_acceptance，发布被拒绝。没有新增人工标签，也没有新交付。

测试覆盖了正常发布、篡改证据、同名输入变化、失败专项、配置保留、禁止重抽、旧索引不修改、缓存隔离、按池量加权、U 风险、checkpoint 中断和分流恢复。具体测试结果归档在 `work/exo_infrastructure_20260921/validation.json`。

基础设施现在可以支撑受控的半自动批次流程。尚未完成：历史全量 CSV 的压缩/迁移、单份底表加窄决策表、全部旧品类执行器迁移、长期存储保留策略，以及业务标注边界本身的修订。本轮不删除历史大表，也不把基础设施测试通过等同于数据合格。
